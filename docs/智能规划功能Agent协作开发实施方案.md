# 目标树智能规划功能 — Agent 智能体协作开发实施方案

> 适用范围：《目标树智能自动拆解重设计方案》《目标树重新规划功能重构设计文档》《目标树智能规划与重新规划整合设计方案》三个功能的落地开发。
> 核心目标：利用 AI 智能体协作（Agent）与技能（Skill）体系，在开发全流程中**严格遵循既定设计规范与项目硬约束**，确保交付质量。

---

## 一、总体协作架构

```
用户（需求方/决策者）
        │ 下达阶段任务、审批方案
        ▼
┌─────────────────────────────────────────────┐
│  主协调智能体（Main Orchestrator，即主对话）      │
│  职责：任务拆分、分派、进度跟踪、结果汇总           │
└─────────────────────────────────────────────┘
   │            │            │             │
   ▼            ▼            ▼             ▼
Explore 子代理  general-purpose  browser_use  Plan 子代理
（代码调研）     子代理（实现）    子代理（UI验证）  （阶段规划）
   │            │            │             │
   └────────────┴─────┬──────┴─────────────┘
                      ▼
        Skill 技能层（按需触发）
  TRAE-code-review / TRAE-security-review
  TRAE-debugger / git-commit / frontend-design
                      │
                      ▼
        质量门禁（vue-tsc / cargo check / 迁移规范）
```

**设计原则：**

1. **单一指挥源**：主协调智能体是唯一的任务分派与合并点，避免多智能体并行修改同一文件产生冲突。
2. **读写分离**：调研类工作交给 Explore（只读、不落盘），实现类工作交给 general-purpose（可写），UI 验证交给 browser_use（只操作浏览器）。
3. **规范前置**：每个阶段开始前，先把该阶段适用的硬约束注入子代理提示词，实现"规范随任务下发"。
4. **门禁后置**：每个阶段结束必须通过质量门禁（见第六章），未通过不进入下一阶段。

## 二、智能体角色分配

| 角色 | 智能体类型 | 职责范围 | 使用时机 | 输出物 |
|------|-----------|---------|---------|--------|
| **主协调者** | 主对话模型 | 阶段任务拆分、子代理分派、TodoWrite 进度管理、结果审核与合并、跨阶段决策 | 全程 | 任务清单、合并后的代码、阶段报告 |
| **代码调研员** | `Explore` 子代理 | 阅读设计文档（大文件分段读取）、检索现有代码模式（如 `build_handler` 合并、`split_service` 现状）、确认字段/命令/组件现状 | 每阶段开工前 | 关键代码位置清单、现有模式说明、风险点 |
| **实现工程师** | `general-purpose` 子代理 | 按明确规格编写前后端代码、执行 `vue-tsc --noEmit` 与 `cargo check` 自检、修复编译错误 | 规格已收敛、文件路径与改动点已明确时 | 可编译的代码变更、自检结果 |
| **UI 验证员** | `browser_use` 子代理 | 启动 `npm run tauri:dev` 后验证 SmartSplitDialog、预览抽屉、不可行处置弹窗的渲染与交互、暗色模式、响应式 | 前端阶段完成、编译门禁通过后 | 截图、DOM 断言结果、交互问题清单 |
| **阶段规划师** | `Plan` 子代理 | 复杂阶段（如三期整合）的实现策略设计、文件清单、依赖顺序、风险权衡 | 阶段复杂或涉及跨层大量改动时 | 实施计划（步骤+文件+顺序） |
| **代码审查员** | `TRAE-code-review` 技能 | 对阶段 diff 做质量/正确性/可维护性/性能审查，输出结构化问题 | 每阶段代码合并后、commit 前 | 结构化审查问题列表 |
| **安全审计员** | `TRAE-security-review` 技能 | 审查新增命令、SQL 拼接、ammonia 净化路径、备份/恢复路径校验的安全性 | 涉及新 Tauri 命令、SQL、用户输入处理时 | 可证实的安全风险列表 |
| **调试专家** | `TRAE-debugger` 技能 | 静态分析无法定位的运行时 Bug（假设→插桩→复现→分析→修复→验证） | 连续两轮静态修复无效后 | 根因分析、修复验证记录 |
| **提交助手** | `git-commit` 技能 | 生成规范化 commit message、智能暂存 | 每阶段门禁全绿、用户确认提交后 | 合规提交记录 |
| **前端设计顾问** | `frontend-design` 技能 | SmartSplitDialog 与预览抽屉的视觉方案（避免通用 AI 审美、暗色适配） | 新建复杂 UI 组件前 | 设计方案/组件代码 |

**角色协作铁律：**

- 实现工程师**不自行检索设计文档**——所需规格由主协调者从文档提炼后写入提示词（避免 400KB+ 文档重复扫描与理解偏差）。
- 任何子代理产出的代码，**必须由主协调者亲自 Read 复核关键文件**后才算合并（Trust but verify）。
- 并行分派仅限**互不重叠的文件集合**（如 Rust 引擎层与 Vue 组件层可并行，同层内串行）。

## 三、技能调用流程

### 3.1 标准调用链（每阶段）

```
阶段开始
  │
  ├─① Explore：调研现状（现有代码模式 + 设计文档对应章节）
  │     └─ 输出：改动点清单、现有模式、硬约束风险
  │
  ├─② （可选）frontend-design：若是新 UI 组件，先出视觉方案
  │
  ├─③ general-purpose × N：分批实现（每批一个内聚改动单元）
  │     └─ 每批必须自检：vue-tsc --noEmit && cargo check
  │
  ├─④ TRAE-code-review：审查本阶段 diff
  │     └─ 高危问题 → 回到③修复；低危 → 记录并评估
  │
  ├─⑤ （条件）TRAE-security-review：涉及新命令/SQL/输入处理时
  │
  ├─⑥ browser_use：UI 阶段做浏览器实测
  │     └─ 交互缺陷 → 回到③修复
  │
  ├─⑦ 质量门禁终检（见 6.1）
  │
  └─⑧ git-commit：用户确认后提交，进入下一阶段
```

### 3.2 技能触发条件（防止滥用）

| 技能 | 触发条件（满足即必须调用） | 禁止场景 |
|------|------------------------|---------|
| TRAE-code-review | 每阶段合并前；用户要求审查 MR/diff | 普通功能实现请求本身不触发 |
| TRAE-security-review | 新增 Tauri command、新增 SQL 拼接、修改用户输入处理/备份恢复/净化逻辑 | 通用代码审查 |
| TRAE-debugger | 同一 Bug 静态分析修复两轮仍失败；用户点名调试 | 简单可静态定位的问题 |
| git-commit | 用户明确要求提交或输入 `/commit` | 主动替用户提交 |
| frontend-design | 新建整页级/弹窗级组件（SmartSplitDialog、ReplanDrawer、不可行处置弹窗） | 小改动、纯逻辑 |

### 3.3 子代理提示词规范（主协调者必须遵守）

每次分派 general-purpose 任务时，提示词必须包含五段结构：

1. **任务目标**：要做什么、为什么（一句话背景）。
2. **文件清单**：要新建/修改的具体路径 + 行号锚点。
3. **规格摘要**：从设计文档提炼的字段/命令/交互规格（如 `SmartSplitRequest` 的字段表）。
4. **硬约束注入**：本阶段适用的项目约束（从 6.2 清单中筛选，逐条列出）。
5. **自检命令**：`npx vue-tsc --noEmit`、`cargo check --manifest-path src-tauri/Cargo.toml`，要求报告结果。

> 禁止出现"基于调研结果自行实现"这类把理解责任推给子代理的表述。

## 四、开发阶段划分

依据整合设计方案的分期能力全景，划分为五个阶段，每阶段有明确的入口/出口条件：

### 阶段 0：规范准备与基线确认（0.5 天）
- **内容**：Explore 代理通读三份设计文档 + 现有 `split_service.rs`、`GoalTreeView.vue`、commands 模块；产出《改动点总清单》与《现有命令/类型清单》。
- **出口条件**：主协调者确认清单完整；确认迁移文件序号（下一个应为 021+）。

### 阶段 1：Rust 引擎层基础设施（零侵入）
- **内容**：快照装配器、约束编译器、可行性判定器、守恒分配器（纯函数化求解器）；新增 `SplitPlan`/`SmartSplitRequest` 类型；**不改动任何现有命令行为**。
- **关键约束**：求解器纯函数化；`build_handler` 合并注册；`panic!/unwrap()` 禁用。
- **出口条件**：`cargo check` 通过；现有 `smart_split/auto_split/split_by_capacity` 行为回归不变。

### 阶段 2：智能拆解前端与命令门面
- **内容**：`SmartSplitDialog.vue`（frontend-design 先行）、拆解预览渲染、确认落库命令、错误码/补救方案展示。
- **关键约束**：任务行 ROW_HEIGHT=36 不破坏；行内图标 flex-shrink-0；`@click.stop`；暗色模式 `dark:` 变体。
- **出口条件**：`vue-tsc --noEmit` 通过；browser_use 验证弹窗完整交互链（配置→预览→不可行处置→确认）。

### 阶段 3：重新规划重构
- **内容**：真实剩余量回填、真实容量计算、预览抽屉（差异表/what-if/影响日历）、plan_hash 防 stale、逐项排除/应用全部、事务提交与回滚、任务锁定保护。
- **关键约束**：预览与提交同源；sqlx 事务 `&mut **tx` 双解引用；幂等重算；触发与执行分离。
- **出口条件**：门禁全绿 + browser_use 验证 what-if 实时重算与回滚链路。

### 阶段 4：整合、自动触发与习惯学习
- **内容**：触发网关（超额完成/频繁改期感知）、跨目标协同分配、DAG 依赖调度、偏好学习、滚动窗口。
- **出口条件**：整合方案验收场景矩阵全部通过（见第八章）。

### 阶段并行策略

```
阶段1（Rust 引擎）──┬── 阶段2（拆解前端）  ← 两阶段可部分并行：
                    │     阶段1 类型定稿后，阶段2 的 UI 骨架即可开工
                    └── 阶段3（重规划）    ← 依赖阶段1 引擎，串行
阶段4 依赖 2+3 全部完成
```

并行时**硬性规则**：Rust 侧与 Vue 侧分派给不同 general-purpose 实例；`src/types/index.ts` 与 `src-tauri/src/db/models.rs` 的类型变更只能在阶段 1 由单一实例完成，前端实例不得改后端类型。

## 五、协作沟通方式

### 5.1 主协调者 ↔ 用户

| 场景 | 方式 |
|------|------|
| 阶段方案审批 | 阶段开始前输出简明计划（改动文件+顺序），用 AskUserQuestion 确认关键分歧点 |
| 进度汇报 | 每阶段结束输出一段式总结（做了什么/门禁结果/下一步），不逐条流水账 |
| 阻塞上报 | 立即上报 + 给出 2-3 个可选解法（含推荐项） |
| 交付物通知 | 文档类交付物用 `computer://` 链接；代码用 `file:///` 行号链接 |

### 5.2 主协调者 ↔ 子代理

- **分派**：单条消息内并行发起多个独立 Agent 调用（`parallel tool calls`），依赖型任务串行。
- **中间指令**：后台代理运行中用 SendMessage 追加要求；不轮询、不空等。
- **回收**：只接受聚合结果；要求子代理回复限制篇幅（如"800 字以内"）防止上下文膨胀。
- **续用**：被中断的任务用 `Agent(resume)` 续跑，不重启重做；已完成的代理仅在新任务需要其历史状态时才续用。

### 5.3 上下文管理

- 大文档（400KB+ 设计文档）**永不直接整读**：由 Explore 分段读取并产出提炼摘要，主协调者只持有摘要与行号锚点。
- 每阶段结束、进入下一阶段前，若上下文已接近压缩阈值，主动用 `new_context` 携带交接说明切换，交接说明必须包含：已完成阶段、关键文件路径、下一阶段任务、失败尝试清单。

## 六、规范检查机制

### 6.1 质量门禁（每阶段硬性检查，全绿才可提交）

| 门禁 | 命令/方式 | 通过标准 |
|------|----------|---------|
| 前端类型检查 | `npx vue-tsc --noEmit` | 零错误 |
| 后端编译检查 | `cargo check --manifest-path src-tauri/Cargo.toml` | 零错误 |
| 命令注册检查 | Grep `generate_handler` / `handlers()` | 新命令已通过 `build_handler` 合并注册，无冲突 |
| 迁移文件检查 | 确认新 `.sql` 文件内容 | 一经提交永不再改（校验和教训）；序号递增 |
| 描述净化检查 | Grep `normalize_description` | 所有 description 写入路径均经净化 |
| CSP 检查 | `tauri.conf.json` + `index.html` meta | 双处一致且未放宽 |
| 代码审查 | TRAE-code-review | 高危问题清零 |
| UI 实测 | browser_use | 主交互链 + 暗色模式无缺陷 |

### 6.2 项目硬约束清单（分阶段注入子代理提示词）

**通用约束（每阶段必注入）：**
- SQLite 连接启用 `PRAGMA foreign_keys = ON`；连接用 `SqliteConnectOptions::new().filename(path).create_if_missing(true)`（中文路径兼容）。
- 命令函数禁止 `panic!`/`unwrap()`，用 `thiserror` 正确返回；内部错误对外脱敏、细节走 `tracing`。
- 所有用户输入经 `validator` crate 校验。
- TS import 置于文件顶部；ARIA 属性加在包裹 div 而非 NCard。

**拆解/重规划专属约束（阶段 1-4 注入）：**
- 求解器纯函数化，快照装配与规划分离，预览与提交同源。
- 数量守恒：分配后总量校验必须存在。
- 重算幂等：重复触发不产生副作用；锁定/进行中任务受保护。
- 事务：sqlx 0.8 双解引用 `&mut **tx`；QueryBuilder 占位符只用 `push_bind()`。
- `plan_hash` 不一致时自动重新预览，禁止提交过期快照。

**前端专属约束（阶段 2-3 注入）：**
- 任务行永远单行、ROW_HEIGHT=36 与 item-size 严格对齐。
- 行内图标 `flex-shrink-0`，点击 `@click.stop`。
- 描述空值不渲染（`v-if`）；`v-html` 仅渲染 ammonia 净化后的内容。
- 暗色模式用 `dark:` 变体补齐；鼓励语居中弹窗而非右下角 toast。
- 任务完成走 `taskStore.completeTask()/backfillTask()`，鼓励逻辑经 `taskStore.maybeShowEncouragement()`。

### 6.3 检查执行方式

1. **自动层**：门禁命令由实现子代理自检 + 主协调者终检双重执行。
2. **审查层**：TRAE-code-review 输出的问题分三级——高危（阻断，必须修复）、中危（本阶段内修复）、低危（记录进阶段报告，由用户决定）。
3. **记忆层**：每阶段结束，新踩的坑/新约定由主协调者**追加写入 project_memory.md**（如新的迁移文件号、新的 UI 约定），确保下一阶段与后续会话自动继承规范。

## 七、异常处理流程

### 7.1 编译/类型错误
```
子代理自检失败 → 子代理自行修复（最多 3 轮）
  → 仍失败 → 上报主协调者，附完整错误输出
  → 主协调者静态分析定位 → 修正分派提示词（常见根因：规格不清/约束缺失）后重派
```

### 7.2 运行时 Bug
```
browser_use 或用户发现缺陷
  → 主协调者静态分析（Read + Grep 定位）
  → 两轮修复无效 → 触发 TRAE-debugger 技能
      假设 → 插桩 → 复现 → 分析 → 修复 → 验证
  → 修复后必须回归该功能完整交互链
```

### 7.3 设计文档与现有代码冲突
```
实现中发现规格与代码现状矛盾
  → 子代理立即停止该点实现（不自行仲裁）
  → 上报主协调者 → 主协调者用 AskUserQuestion 向用户呈报冲突
      选项：遵循设计文档改代码 / 尊重现状调整设计 / 折中
  → 决议结果写入阶段报告并同步 project_memory
```

### 7.4 子代理产出不合格
```
主协调者复核发现未按规格实现
  → 小偏差：主协调者直接 Edit 修正
  → 大偏差：Agent(resume) 带明确修正指令续跑该代理
  → 提示词本身缺陷：更新提示词模板条目，重派新代理
```

### 7.5 多实例环境冲突
- 警惕 `tauri:dev` 多实例争抢日志文件（os error 5）：browser_use 验证前确认唯一 dev 实例在跑。
- 沙箱阻断 SQLite journal 写入时，按既有经验申请权限或绕过沙箱，不盲目重试。

### 7.6 数据迁移事故
- 任何迁移校验和不匹配 panic 风险：迁移文件提交前主协调者亲自 diff 确认；已应用的迁移文件**永不修改**，需要变更时新增迁移文件。

## 八、验收标准

### 8.1 阶段验收（每阶段出口）

以 Given-When-Then 形式核验本阶段核心能力，例如：

- **阶段 1**：Given 一个含已完成任务的目标，When 装配快照，Then 剩余量 = 总量 − 已完成回填量（守恒校验通过）。
- **阶段 2**：Given 时间预算不足的目标，When 提交拆解，Then 不报错终止，而展示按成本排序的 ≥3 个补救方案，采纳后自动重算。
- **阶段 3**：Given 预览期间外部数据变更，When 提交，Then 检出 plan_hash 不一致并自动重新预览；Given 已提交的重规划，When 用户撤销，Then 数据完整回滚。

### 8.2 总体验收（对齐整合方案能力全景）

**拆解域：** 产物可直接执行、感知真实上下文、安全重入、非线性节奏、约束完整、不可行给方案、越用越准、数量守恒、可解释、跨层级拆解。
