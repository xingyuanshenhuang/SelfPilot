# 设置视图新增"跳过任务后的处理方式"（A/B/C 模式）实现方案

## 需求背景

在"设置"视图新增一个行为设置项：**跳过任务后的处理方式**，提供三种模式：

- **模式 A（默认）**：标记未完成，允许之后补完成，不重新计算剩余任务。
- **模式 B**：自动将任务延后到后续日期。
- **模式 C**：自动将剩余任务量平均分摊到剩余天数。

本文档描述该功能从现状到落地的完整实现路径、涉及的代码位置、执行顺序和验收标准。

## 现状基线

当前系统对"跳过任务"的处理实际上就是模式 A。`skip_task` 命令（`src-tauri/src/commands/task.rs` 第 127–145 行）只做一件事：把 `status` 置为 `skipped`，不碰 `plan_date`、`plan_qty`、`actual_qty`，也不触发任何重新规划。补完成由 `backfill_task`（同一文件第 242–292 行）承担，它明确允许对 `skipped` 任务补录实际完成量，且只更新 `actual_qty` 与 `status`，不联动未来任务。

进度与统计层面对 `skipped` 的统一约定（`src-tauri/src/services/progress_service.rs`，以及 `src-tauri/src/commands/stats.rs`）：`skipped` 任务不计入 `total_plan`、不计入 `total_actual`，多数列表查询也排除它。这形成了一个稳定的契约：**跳过的任务从计划视野中退出，但数据库记录保留，随时可补完成**。

基于这个基线可以得出一个关键结论：**做 A 模式不需要改任何核心命令**，只需补上"设置项 + 设置界面"；B、C 才需要新增行为逻辑。

## 总体设计

### 设置存储

复用现有的 `settings` key-value 表（`src-tauri/src/db/models.rs`），新增一个键：

```
key:   default_skip_mode
value: "A" | "B" | "C"
```

这是通用的 key-value 表，新增键不需要数据库迁移，也不触碰 `_sqlx_migrations` 表，规避既有迁移校验和相关的风险点。

缺省处理：读取不到该键时按 `"A"` 处理，保证升级后行为与现状一致。

### 模式分发位置

在前端，跳过任务的调用点有 3 处：`TaskItem.vue`、`CalendarView.vue`、`GoalTreeView.vue`，它们或走 store、或直接调 `taskApi.skipTask`。为最小化改动并保持逻辑一致，把模式分发放在**后端 `skip_task` 内部**：命令开头读取 `default_skip_mode`，按三种模式走不同分支。前端调用点与命令签名保持不变。

### `skipped` 状态在 B/C 中的取舍

- **B（延后）**：任务从"该跳过"变为"挪到后面再做"，因此不应停留在 `skipped`。做法是 `plan_date` 向后平移到下一个有效日期，`status` 恢复为 `pending`，量保持不变。
- **C（均摊）**：被跳过的当日任务并入"剩余量"，参与后续天数的重新分配；`skipped` 语义继续沿用，重排逻辑只作用于 `auto` 且 `is_manual = 0` 的任务。

这样 B/C 都不破坏 `skipped` 的既有契约，也不新增状态枚举，改动面可控。

## 模式 A 实现

### 改动点

A 的核心行为已存在，无需新增命令。要落地的是"可配置 + 界面能选"：

1. **后端**：`skip_task` 读取 `default_skip_mode`，当值为 `"A"`（或缺省）时走现有分支，行为与今天完全一致。
2. **前端设置界面**：`src/views/SettingsView.vue` 新增一个设置卡片；三档单选使用现有的 `NRadioGroup` / `NRadioButton`（该文件顶部已 import）。
3. **前端状态与 API**：新增页面级状态读取/写入设置值，保存走现有 `settings.ts` 的 `setSetting/getSetting`。

### 代码要点

`skip_task` 的分支骨架：

```rust
#[tauri::command]
pub async fn skip_task(task_id: String, state: State<'_, DbPool>) -> AppResult<Task> {
    let mode: String = sqlx::query_scalar(
        "SELECT value FROM settings WHERE key = 'default_skip_mode'"
    )
    .fetch_optional(&state.0)
    .await?
    .unwrap_or_else(|| "A".into());

    match mode.as_str() {
        "B" => skip_by_defer(task_id, &state.0).await,
        "C" => skip_by_resplit(task_id, &state.0).await,
        _ => skip_by_mark(task_id, &state.0).await, // A：现有逻辑
    }
}
```

A 分支 `skip_by_mark` 即现在的实现，不做改动。

## 模式 B 实现（自动延后）

### 行为定义

被跳过的任务不标记 `skipped`，而是把 `plan_date` 向未来平移，`status` 恢复 `pending`，`plan_qty`、`actual_qty` 不变。平移的天数以目标剩余计划分布为准，初版取固定偏移（新增设置 `skip_defer_days`，默认 1 天）或顺延到下一个尚未排满的日期。

### 数据与边界

- `plan_date` 平移后，同步处理 `overdue_date`（清空或一并平移，避免逾期列表把新计划日期误看成逾期）。
- 平移后的日期不晚于目标截止日；若已到截止日，则退化为标记 `pending` 留在最后一天，不强行超出。
- 尊重 `is_manual = 1`：手动任务不被自动重排，只平移自身日期即可，避免触及其他任务。
- 允许后续仍用 `backfill_task` 补完成（它按新 `plan_date` 与 `actual_qty` 判状态）。

### 命令签名

```rust
async fn skip_by_defer(task_id: String, pool: &SqlitePool) -> AppResult<Task>;
```

事务内执行：更新 `plan_date` / `overdue_date` / `status`，返回更新后的任务供前端局部刷新。描述性增强（如弹窗提示"已顺延至 X 日"）放在前端返回值上处理。

## 模式 C 实现（剩余量均摊）

### 行为定义

被跳过的当日任务并入"剩余任务量"，然后按目标**剩余天数**把剩余量重新平均分配到后续每天，只调整 `auto` 且 `is_manual = 0` 的任务的 `plan_qty`；`is_manual = 1` 的任务保留原计划量（其原量从剩余量中先行扣除）。`skipped` 语义、进度查询、统计排除逻辑都不变。

### 复用与差异

现有 `build_replan_preview`（`src-tauri/src/services/split_service.rs` 第 351–485 行）和 `split_goal_into_tasks` 提供了"按量均分"与"自动/手动分流"的核心算法，但前者按"待重新分配的任务数"而非"剩余天数"分配。因此需新增一个轻量函数，按剩余天数口径分派：

```rust
pub fn resplit_remaining_to_days(
    goal: &Goal,
    unfinished: &[Task],   // 该目标下 pending/partial 的 auto 任务
    manual_total: f64,     // is_manual=1 任务的 plan_qty 合计
    completed_qty: f64,
    remaining_days: i64,   // 今天到 deadline 的天数
) -> ResplitPreview;

// base = floor(remaining_qty / remaining_days)
// remainder 分配给前若干天,写法与 split_goal_into_tasks 一致
```

其中 `remaining_qty = goal.total_qty - completed_qty - manual_total`。

### 边界

- `remaining_days <= 0`（已过截止日）时不做重排，退化为 A 的 `skipped` 行为并提示。
- 重排后每日 `plan_qty` 四舍五入为 0 的天直接跳过（与既有均分逻辑一致）。
- 只更新被选中任务的 `plan_qty`，不新增、不删除任务行，降低对日历、依赖链、进度缓存的影响面。
- 建议把"该次跳过自动重排"作为一次性行为，不做持久化的周期性重算。

## 执行顺序

分三步落地，前一步可独立上线、独立验证：

1. **模式 A + 设置界面**：完成 `settings` 键、分发骨架（A 分支）、设置卡片 UI。这一步即可交付，功能等价现状，只是把语义显式化成选项。
2. **模式 B**：实现 `skip_by_defer` 与 `plan_date` 平移，接入分发分支。
3. **模式 C**：实现 `resplit_remaining_to_days` 并接入分发分支。

每一步完成都跑通 `cargo build`（`src-tauri`）与前端构建，避免一次性引入大改动难定位问题。

## 验收标准

- **模式 A**：跳过任务后 `status='skipped'`，今日/逾期/日历列表不再展示；目标任务总量与后续每日计划不变；`backfill_task` 可对该任务补完成，补完后进入 `done/partial/pending` 并按新量计入进度。
- **模式 B**：跳过后任务 `plan_date` 顺延且 `status='pending'`，量不变；顺延日期的任务在日历正确出现；截止日边界不越界。
- **模式 C**：跳过后剩余量重新平均到剩余天数，每日 `plan_qty` 之和等于剩余量；手动任务不受影响；进度百分比随新计划重算且数值合理。
- **设置持久化**：重启后仍保留所选模式；未显式设置时行为等价当前（即模式 A）。

## 风险与注意事项

- **不新增数据库迁移**：全部改动只依赖现有 `settings` 表与 `tasks` 表字段，避免触碰 `_sqlx_migrations` 校验和（项目已有因此 panic 的教训）。
- **事务一致性**：B/C 的所有写操作放在同一事务内，避免"改了一半"导致状态不一致。
- **进度与统计**：B 因为把任务恢复为 `pending`，它会重新进入 `total_plan` 与逾期/今日列表，这与 A 完全不同——这是设计预期，但需要在验收时确认统计口径符合预期。
- **手动任务**：C 的重排必须跳过 `is_manual = 1`，否则会覆盖用户手动设定，违背既有约束。
- **B 的堆积问题**：连续多次延后可能在某一天堆积过量任务，初版对单次顺延的任务数不加限制，但需在前端对顺延后的任务给出可见提示（如预计量偏高）。
